# The game in Godot

The action RPG and village life sim (`docs/vision/game-design.md`) is built in Godot 4.7.2, in the top-level `game/` folder. The Expo app stays as it is for now; world, quest and combat work moves here. Decisions behind it (Matt, 21 to 25 Oct): desktop first, landscape only, a 960 x 540 art grid (density 3, so 320 x 180 world px) shown at exactly 2x on 1920 x 1080 and 4x on 4K, HiDPI on; LimboAI, Phantom Camera and GdUnit4 adopted; maps from the Python art kit (or Tiled with YATI later).

## Commands

Everything runs headless; no editor is needed.

```sh
export GODOT=$(bash game/tools/get_godot.sh)      # pinned 4.7.2, SHA-512 checked, self-contained mode
npm run check:godot                               # import, run the main scene 300 frames, GdUnit4 tests
npm run playtest:godot                            # play the whole build with real keys and mouse (below)
$GODOT --headless --path game --import            # re-import after adding or changing art
$GODOT --path game -- --fresh --zone=woodland --spawn=stones   # play (needs a display)
```

`check:godot` (`game/tools/check.sh`) fails on any `SCRIPT ERROR` or engine `ERROR:` line, not only on the exit code, and runs a byte-identical private copy of the selected executable. Before even `--version`, it copies only the executable into an empty private directory, checks the bytes and executable permission, and refuses setup failures with exit 2. It never copies portable markers, `editor_data`, settings or player profiles. Each version/import/main/GdUnit child receives fresh private HOME, XDG config/data/cache and TMPDIR directories; the runtime is removed on exit. It is not part of `npm run verify` (that needs no Godot); the `Godot` GitHub Actions job (`.github/workflows/godot.yml`) runs it on ready PRs and on `main` when `game/` changes. Draft PRs run no CI, so run it locally before marking a PR ready.

Game options, after `--`: `--fresh` ignores the save, `--play=<route file>` hands the keys and the mouse to the play driver (below), `--zone=<id>` and `--spawn=<name>` choose where to start, `--shot=<png>` waits 2 s (`--wait=<s>` to change), saves the whole window 1:1 and quits; `--demo` walks the player right, down, left and up with a bow shot after each (`--quit` to end after it). For a video that keeps real time on a slow machine, use the movie maker: `DISPLAY=:96 $GODOT --path game --audio-driver Dummy --resolution 1920x1080 --write-movie out.avi --fixed-fps 30 -- --fresh --demo --quit`. The picture and demo modes (`--shot`, `--demo`, `--lineup`, `--cycle`, `--bossfight`, `--telegraph_shot`) never write the save, with or without `--fresh`.

**Screenshot recipe** (the container has no display):

```sh
Xvfb :96 -screen 0 1920x1080x24 &                 # start it yourself, once
DISPLAY=:96 $GODOT --path game --audio-driver Dummy --resolution 1920x1080 --position 0,0 \
  -- --fresh --spawn=stones --shot=/path/to/woodland_1080.png
```

Use `--resolution 3840x2160` (on a matching Xvfb screen) for 4x, and an odd size such as `1600x900` to see the sharp-bilinear fallback.

`npm run review:scene -- <zone>` uses the caller's nonempty `DISPLAY` and preserves
`XAUTHORITY` for both import and capture. This also supports an authenticated local
TCP display such as `DISPLAY=localhost:96.0` when Unix X sockets are unavailable;
the caller must start the server, configure its authentication and transport, and
stop it afterwards. The runner never stops a caller-managed display. With no
`DISPLAY`, it starts its existing local Xvfb fallback and terminates and reaps only
that process. In both cases its XDG configuration and data directories are
disposable; it does not change the parent environment.

The scene runner keeps import and per-spawn stdout/stderr in `render-import.log`
and `<zone>_<spawn>.log` under `--out`. It removes prior capture outputs before
rendering and rejects failed commands, engine-error logs, missing or stale shots,
and invalid PNGs. Render failure writes an `incomplete` report with the existing
detector findings and diagnostics, and exits 2; exit 1 still means blocker/fault
findings and exit 0 means no such findings. A composite alone does not establish
requested capture coverage. A previous report is removed before new work, so an
earlier success cannot stand in for a failed producer. Crop sheets round only the
pixel slice bounds outwards for fractional findings, keeping the finding boxes;
invalid, empty or wholly outside boxes get a labelled unavailable cell.

## Playing with real input (10 Nov)

A test that calls methods is not proof that something plays. `npm run playtest:godot` (`game/tools/playtest.sh`) plays the build the way a player does and fails, with the step's name and the game's state, at the first step that does not work:

```sh
export GODOT=$(bash game/tools/get_godot.sh)
npm run playtest:godot                                  # every route in game/tools/routes/
npm run playtest:godot -- game/tools/routes/main.txt    # one route
```

- **The driver** (`game/tools/play_driver.gd`) is a node `game.gd` adds for `-- --play=<route file>` (`--play-out=<dir>` for its log and pictures, `--play-follow` to keep reading lines appended to the file, for steering a session by hand). It sends real `InputEventKey`, `InputEventMouseMotion` and `InputEventMouseButton` events: WASD to walk, E to talk and to step through lines, Space to roll, the mouse to aim and shoot, Esc for the menu. It reads the screen through `HUD.shown_text()` (the tracker, the prompt, the title card), so `expect hud ...` checks what is drawn, not what the model holds. The driver's limits (a walk's 25 s plus distance / 30, `fight N`, `down N`) and the times in its log are game time, counted in physics steps, so a loaded machine that runs the game slowly does not fail a walk; only the runner's one limit per session (`PLAYTEST_TIMEOUT`, 900 s) is on the wall clock. `--play` works in debug builds only (`OS.is_debug_build()`): an exported release build ignores it.
- **Walking** uses `game/tools/walk_grid.gd`: the player's body circle against the real walls on a 6 texel grid, A* over the free cells, steering at the furthest point of the plan in sight. `goto x y` fails when there is no way there.
- **A route** is a text file, one command a line (`step`, `goto`, `door`, `talk`, `fight`, `down`, `hurt`, `button`, `defend`, `key`, `hold`, `aim`, `click`, `roll`, `wait`, `shot`, `expect ...`, `restart`, `end`; the driver's header lists them). `button <name or text>` clicks an on-screen button with the real mouse, through the pixel screen's scale (the raid's prepare screen); `defend` fights a raid's waves as they come until the night is over. `restart` closes the window as a player would; the runner starts the game again without `--fresh`, in the same private profile, and the route carries on at the next line. That is how quitting and loading are played. `fight` rolls or steps out of the lane of a telegraphed attack and, when downed, walks back and goes on (the log counts the downs); `down` takes every hit on purpose.
- **The routes:** `routes/main.txt` plays the whole build in order from a fresh save to the closing card, restarting after every step that moves the story and being downed once at each of the three fights (about ten minutes). `routes/wrong_order.txt` goes to Crossroads before the sign and before Hale, clears the camp before reading the sign, quits in the middle of a line and presses keys under the pause menu. `routes/world_fixes.txt` is hurt at the camp (`hurt`: until the first hit lands), rests at the hut, quits and loads, slides along the foot of the garden walk's wall and walks back to the woodland. `routes/crossroads_first.txt` takes the sign's pouch, pays for the forge in Crossroads before meeting Hale, then talks to her (the orders the slice allows with "or already visited" and "or already restored"). `routes/first_night.txt` starts from a save made just after Home again (`#! save: first_night.save.json`, a save from before raids, so loading it is the migration too), walks out and back in until the first night is announced, puts it off twice, quits on the prepare screen, rings the bell and defends the three waves (`defend`) to the win and Hale's offer of the bell tower.
- **Header lines** before a route's first command start it somewhere other than a fresh game: `#! save: <file>` copies that save (beside the route) into the route's private profile in place of `--fresh`, and `#! args: ...` adds engine arguments to every session of the route.
- **The runner** needs a display. With `DISPLAY` set it uses it; without, it starts its own Xvfb (`PLAYTEST_DISPLAY`, default `:97`) and stops it afterwards. It runs a private copy of the executable with a private HOME and XDG profile per route, writes to `game/reports/playtest/<route>/` (`log.txt`, `godot.log`, `result.txt`, the pictures, `fail.png`), and fails on any `SCRIPT ERROR` or engine `ERROR:` line as `check.sh` does. It plays in real time and is not part of `check:godot` or `verify`.
- **When you add or change a quest, a talk area or a door:** extend a route (or add one) and run it. Positions are global positions in texels, as the zone scenes have them; `info` in a route logs every talk area, door, spawn and enemy of the zone with its position.

Two GdUnit suites hold the same ground without a display. `test/story/test_story_model.gd` walks every state a player can reach by doing what the three zones offer in any order (who is there comes from the zone scenes and their Conditionals, what can be walked to from the walls) and fails if any order strands the player, if a quest can start and never finish, if the HUD ever has nothing to say or if a written line can never show. `test/test_reach.gd` checks that every talk area, open door and spawn can be walked to in every stage and that the prompt shows a step short of each thing.

## Traps (from the evaluation slice)

- **A `SCRIPT ERROR` does not stop a run.** Godot logs it and carries on, and still exits 0. Always scan the log (check.sh does). `--quit-after <frames>` ends a run; `get_tree().quit()` from a script is the other way out.
- **No `-d` for headless test runs.** With the debugger on, a parse error drops into Godot's interactive `debug>` prompt and the run hangs; `--remote-debug` to a closed port now logs errors of its own. check.sh runs GdUnit4 without either.
- **Godot writes to `~/.config/godot` and `~/.local/share/godot`** whenever it runs. Portable mode (an empty `_sc_` file beside the binary; `get_godot.sh` adds it) can override XDG paths. `check.sh` therefore uses the verified executable-only copy described above, without portable markers, and fresh private roots for every child. Direct engine commands in the recipes above do not acquire that wrapper isolation. The game's own `user://` is `~/.local/share/napattack` (`config/custom_user_dir_name`).
- **Node paths into an instanced scene** (`NodePath` exports such as a camera's follow target) only resolve when the instance has editable children, and break silently when the inner scene changes. Bind them in code (`pcam.follow_target = player` in `game.gd`) or use groups (`get_first_node_in_group("player")`).
- **Headless frames are unthrottled.** In tests, wait on `get_tree().physics_frame`, not process frames, before checking anything physics does (areas, movement, timers on physics).
- **Hand-written `.tscn` files** are fine (the generator writes them) but use `format=3` and string ids; the editor adds `uid=` on save. Commit the `.uid` and `.import` files Godot creates; never commit `game/.godot/`.
- **A missing autoload is a compile error** in scripts run with `-s` (they compile before autoloads exist): reach autoloads through the tree, or run a scene.


**The screen.** The world renders into a 960 x 540 SubViewport. `pixel_screen.gd` scales it to the largest size that fits with the aspect kept: a whole number shows with plain nearest filtering (2x at 1080p, 4x at 4K), anything else with the sharp-bilinear shader, so odd windows fill instead of showing wide black bars. The save's `settings.pixel_scale = "whole"` forces whole scales with bars. Project stretch is off because this node does the scaling. The HUD and dialogue box draw inside the art grid for now.

**Units.** One world px is 3 texels. Gameplay constants are written in world px times `DENSITY` (`50.0 * DENSITY`), so they read like the design doc.

## Systems

- **Input** (`core/inputs.gd`): the 11.5 map in code. WASD or arrows and the left stick move; the mouse or right stick aims; left click or X attacks; right click or right trigger is ranged (bound, not built); Space or A rolls; Q or right bumper special; F or left trigger familiar; R or left bumper tonic; E or Y interact; Esc or Start pauses; M map; Tab gear. Dialogue advances on E, Enter, A or Y, never Space or click.
- **Player** (`actors/player.gd`): run 50 world px/s; a 0.42 s roll invulnerable for its first 0.26 s, two charges each back after 1.2 s; a three-swing combo with a heavier finisher; hit-stop of 4, 4 and 7 frames (halved under reduced motion); mercy frames after a hit; no naps at 0 HP (the player gets up at the zone's start). The body is Bramble from the redrawn cast (below): facing from movement or aim, clips by state (idle, walk, the bow shot on left click, dodge for the roll, hit, defeat before getting up), walking at the manifest's `walk_speed`. The melee combo stays in code for the billhook but is not bound.
- **Enemy** (`actors/enemy.gd`): the evaluation's LimboAI state machine (idle, chase, a 0.5 s telegraphed wind-up, lunge, recover, leash home), dying at 0 HP and reporting to its camp. The rules for going home, healing, waking to a shot, reach (an arrow glances off an enemy that cannot come for the archer), steering round solids and the given-up chase are the same for the mossling and the Undercroft's creatures (`enemies/slice_enemy.gd`) and are listed, with the test that holds each and what is still open, in `game/enemies/README.md`.
- **Camera** (`game.gd`): a PhantomCamera2D following the player with damping, pixel snapping, the zone's bounds as limits, aim look-ahead up to 48 world px past a 16 px dead zone (11.2), and a 1 world px shake on hits (off under reduced motion).
- **Save** (`core/save_game.gd`): one versioned JSON document, `user://save_0.json`, written to a temporary file and renamed. `data` holds zone, spawn, Glint, flags, quests, the tracked quest, player and settings. When a field changes shape, bump `VERSION` and add a step to `_migrate`. The save is read once, when the process starts (`--fresh` skips it); the game scene plays what is in memory and never reads the disk, so a test that instances it gets the state the test set. The game autosaves when a quest moves, when a building is restored, when the zone changes, and when it is closed (the window's close button or Quit in the pause menu). A loaded game has the hearts the save had (10 Nov: it used to heal to full). A save file that cannot be read is copied to `save_0.json.broken` before the new game writes over it, and a save from a newer version of the game is left alone (the game then cannot save); either way a card says so at the start instead of beginning again silently (`SaveGame.boot_error`). What a save does not hold: where in the zone the player stood (a load starts at the spawn the zone was entered by) and a camp that is only partly cleared (its enemies stand again).
- **Zones** (`core/zones.gd`, `world/zone.gd`, `world/door.gd`): `data/zones.json` maps ids to scenes. `Zones.go_to(id, spawn)` swaps the zone, moves the one player into its `Actors` at the spawn marker and records it in the save. A door to a zone not in the table is refused with a warning (Crossroads' west road to Valley Halt waits for act 1). A door's `only_if` condition keeps it shut until it holds (the Undercroft's hatch). Entering a zone sets the flag `visited:<zone>`. A player who arrives at a spawn beside a door (within 120 texels) looks away from that door, into the zone; a mouse or a stick aims again as soon as it is read.
- **Quests** (`core/quests.gd`): JSON in `data/quests/`. The world reports plain events (`talk:<speaker>`, `camp:<camp>`, `enter:<zone>`); a quest starts on its `start.on` event, each step completes on its `on` event (if its `if` condition holds) or at once when its `done_if` already holds; rewards pay Glint and set flags. Conditions (`flags`, `not_flags`, `done`, `active`, `not_started`, `step`) are shared with dialogue; zone plans, zone scenes and `data/leads.json` may also use `started` (active or done), `past` and `not_past` (`[quest, step]`: the quest has left that step behind), which `scripts/narrative/validate.py` does not accept in quest and dialogue files. The flag `zone_built:<zone>` is never saved: it holds while that zone is in `data/zones.json`, and a quest whose places are not built asks for it in `start.if`, so it cannot start and then wait on things that do not exist (*Bread for the Col hut* waits for the Frostline). Quests never expire and never run on a clock (8.3). A quest's optional `next_visit_flags` are set the next time any zone loads once the quest has started (`Quests.zone_loading`, called by `Zones.go_to`): *The road home* sets `hale_walked_home` that way, so Hale stays on the woodland path while the player is still there and is in Crossroads from the next load, never in both and never gone as her line closes. The HUD tracks the active quest that moved last (`SaveGame.data.tracked`); with none active it shows a lead, the first entry of `data/leads.json` whose condition holds, so there is always a line saying where the story goes on. The same file holds the title cards (`cards`): the opening on a new game and the closing beat when this build's last quest is done, each shown once a save, top centre, without stopping play (`HUD.show_card`; not under `--shot`, `--demo` and the other picture modes).
- **Dialogue** (`core/dialogue.gd`, `ui/dialogue_box.gd`): JSON in `data/dialogue/`, per speaker a name and entries; the first entry whose condition holds is shown, then `talk:<speaker>` goes to the quests. An `Interactable` (`world/interactable.gd`) shows a "!" while a quest waits on it (the quest's own conditions included: a quest that cannot start yet raises none). No talk area is smaller than `Interactable.REACH`: each adds an internal circle of 60 texels round the node beside the shape the scene or a plan's `radius` gave it, so the prompt shows about a body height away. The scene's own shape is not changed (the world editor reads and writes it); one larger than 60 still reaches further. Where areas overlap, the prompt goes to the one a quest waits on, then to the nearer.
- **Village** (`core/village.gd`, `world/restore_site.gd`, `world/conditional.gd`): zone plans in `data/plans/` list `restores` (cost in Glint, optional condition) and `stages`. A `RestoreSite` ("restore here") pays and restores instantly, records the tier in `SaveGame.data.village.restored` and reports `restore:<id>`. A mark hides, gives no prompt and takes no Glint until its restore's own condition holds (`restores[].if` in the plan, which `RestoreSite.asked()` and `Village.can_restore` both read). The forge has no condition and the Ferns' door only waits for the shard, so both can be paid before their quests ask (the slice's "or already restored"); the apothecary waits for Morel to ask, because its 40 Glint paid early could leave the forge or the Ferns' door out of reach. `restore_sites[].if` stays the plain "not restored yet" the kit's seed pieces read (`scripts/art/kit/seed_props.py`); after changing a plan's restores or sites, run `gen_village.py`, then `python3 -m scripts.art.kit.seed_props --force` and `python3 -m scripts.art.kit.props`. The Glint a mark's lines quote (`restore_<id>` in the dialogue) must equal the plan's cost. A `Conditional` node shows and enables its children only while its condition holds, so one scene holds the broken and the restored town. The forge's fire and the smithy's smoke also wait for `hale_walked_home` (`TENDED` and `SMOKE` in `gen_village.py`): a forge paid while Hale is still on the woodland path has no flame until the zone load that brings her home. A plan thing with `"rest": true` is a `RestSpot` (`world/rest_spot.gd`; the hut's doorstep): E gives full hearts and saves, for nothing and as often as wanted, with no prompt while a living enemy is within 480 texels, while the player flinches from a hit or while a line is open (one line, true whether or not a heart was missing); the world dims for under a second, not under reduced motion. Conditions also take `restored`, `not_restored` and `glint_at_least`.
- **Camps** (`world/camp.gd`): a node whose child enemies count as one fight; clearing it sets `camp_cleared:<id>` and reports `camp:<id>`; a cleared camp stays empty. Each creature freed pays Glint once for the life of the save (2 a mossling, 3 an Undercroft creature, 10 the Thornback: `data/balance/glint.json` "fights"; the save's `paid` holds `<camp>/<name>`), so a camp that is back after a zone reload or a defeat pays nothing twice.
- **Going down** (`core/glint_cache.gd`, `world/glint_cache_pickup.gd`): the player gets up at the zone's start with every heart, and a fifth of the Glint carried (rounded down) stays as a cache where they fell. Caches are in the save (`caches`: zone, x, y, glint), stay until walked over, and a second defeat adds a second one. `game.gd` drops the cache in `_on_downed` and sets the pickups out in `_on_zone`; the HUD's count tints for half a second on a change (not under reduced motion). `test/test_glint_cache.gd` holds it, and `test/story/test_story_model.gd` plays every order of the story with the worst defeats in it.
- **Raids** (`core/raids.gd`, `world/raid_night.gd`, `enemies/raid_creature.gd`, `ui/raid_screen.gd`; game-design.md 7.6, vertical-slice.md beat 8): a raid is JSON in `data/raids/` (the first night: its lane and pads by the Crossroads plan's ids, its defence kinds, the lantern's health, three waves of the woodland's creature roles, the brief repairs, the reward; every number a placeholder) and its purse is in `data/balance/glint.json` (`raids`). The save holds one raid at a time (`raid`: id, state, postponed, wave, layout, repairs; a save from before raids loads as `none`, nothing pending). Attention comes from the lit lantern (`shard_home:woodland`); once Home again is done the raid is announced on the next walk into Crossroads from another zone (a load or getting up is not a walk in), as the prepare screen: untimed, both pads filled with Hale's hurdle barricade (a tap cycles a pad through the kinds the player has, then empty), "Ring the bell", and "Not tonight" twice; after two it is due on the next walk in, with the screen still first. Ringing stands the hurdles (low solids: feet stop, arrows fly over) and gives the lantern a health bar; `RaidNight` sends the waves from the halt road, each when the last is freed. Its creatures are `SliceEnemy` with a march: they walk the lane, batter a standing hurdle or the lantern with their own wind-up, turn on the player near them with the camps' approach and strike under the shared cap of two, never target a villager, and are freed with the camps' look. Win: the purse once, `first_night_won`, and the bell tower offered as a stage-1 restore (Hale says so; its mark and picture wait for stage 1). Loss (the lantern falls, or the player goes down, who keeps the usual cache rule): brief repairs (boards on the smithy's window, a cart on its side) until the next walk in, which offers the night again. Walking out mid-night leaves it due; quitting mid-night brings back the screen, from wave 1. The hurdle, the lantern's bar, the repairs and the screen's lane map are placeholders in the blockout's colours (art follow-up). `test/test_raids.gd` holds the rules; `routes/first_night.txt` plays them.

## The cast

The characters are drawn and animated by Claude A's procedural rig outside the repo (the castwork: one pose-driven build per character, renders S, N, E and W from the same pose, 17 clips, timings fitted to Codex's studio). `python3 game/tools/import_cast.py <castwork>/out bramble` copies one character into `game/assets/characters/<id>/`: a strip per clip and facing (`sheets/<clip>_<F>.png`, 160 x 144 cells, foot pivot (80, 136)), `frames.tres` (animations `<clip>_<F>` as AtlasTexture regions) and `manifest.json` (per-drawing durations, release frames and times, anchors such as `arrow_tip` and `hand_R` in pixels from the foot pivot, `walk_speed`). It checks each frame's size and sha256 against the manifest.

`actors/cast_sprite.gd` (`CastSprite`, an AnimatedSprite2D) loads a character and keeps time from the manifest itself, so gameplay can ask which drawing is showing and where its anchors are; `CastSprite.facing_for(v, current)` picks the nearest of the four body facings (S, N, E, W) with 10 degrees of hysteresis round the current one (animation contract v2, castwork CONTRACT.md; Matt 26 Oct: four directions like Eastward, the weapon in more). Weapon clips (the manifest's `aim_clips`, Bramble's bow shot) are also drawn at five aims within each facing, every 22.5 degrees (16 directions): `play_clip` shows `<clip>_<F>_<tag>` for the aim (`set_aim`, or the parent's `_shot_dir` while shooting, or its `aim`), and `anchor()` reads that aim's drawings, so the arrow leaves from the aimed arrow tip and flies along the exact aim. Turns are smooth (Matt, 26 Oct, after Eastward's gameplay): when the facing changes in idle, walk or a weapon clip, the sprite shows the stored three-quarter drawing between the two facings (`<clip>_<D>`, the manifest's `turn_inbetweens`) for 0.07 s, keeping the drawing index and clip time, and a reversal passes through one side in three 0.055 s steps (`CastSprite.turn_steps`); a weapon aim that changes mid-clip steps one aim per 0.04 s. Bramble and Velvet are the v2 pilots (12-drawing walks, more drawings with anticipation and follow-through, walk speed 78.1 px/s, idle fidgets: after 4 s of idle the sprite plays one and returns to idle, any other clip cancels it). A manifest with eight directions (the stored three-quarter work) still plays them (`facing_for8`, `resolve_facing`). The player spawns its arrow (`actors/arrow.gd`) on the primary's `release_frame`, at that drawing's `arrow_tip` (or the drawing before, once the arrow has left the bow), flying along the aim; `test/test_cast.gd` checks the facing choice and hysteresis, the turn in-betweens (path, held stride), the aim chosen within the facing (16 directions), the release frame and position in every facing and at off-facing angles (the arrow leaves the aimed `arrow_tip` and flies along the exact aim), the idle fidget, the walk speed, the dodge and hit clips and that defeat plays before `downed`.

All fourteen are imported (`python3 game/tools/import_cast.py <castwork>/out`, 26 MB). **Character select (debug):** keys 1 to 0 pick Bramble, Iona, Pendle, Cairn, Morel, Velvet, Tam, Mirra, Brine and Ashe, and Shift+1 to 4 pick Clack, Nix, Rook and Mote (`Player.CAST`; the label at the bottom left names the current one). Bramble keeps his wired bow shot; the others play idle, walk, primary (no projectile or effect yet), dodge, hit and defeat until the ability runner lands. `--lineup` stands the whole cast in a row, and `--cycle` turns the player into each one in turn (walk, primary, walk back), and `--character=<id>` starts as that one.

Scale: the cast is drawn at the 960 x 540 grid's own scale (Bramble 74 texels tall), and its walk speed is in texels a second (Bramble 68, the speed at which his planted foot does not slide). That is slower than the design's 50 world px (150 texels) run; a faster run needs a run cycle with a longer stride, not a faster walk.

## How lanes add a region (zone)

1. Render the zone with the kit at density 3 and import it: `python3 game/tools/gen_zone.py <zone> --render <kit checkout> --walk <kit checkout>/lib/zone-maps.ts`. It runs `python3 -m scripts.art.native.zone --zone <zone> --density 3` in the kit checkout, copies the pictures to `game/zones/<zone>/art/`, keeps the kit's boxes in `kit.json` and the walk mask in `walk.txt`, and writes `<zone>_base.tscn`: ground and water below everything, the objects y-sorted with their drawn feet as origins, the solids, and the named stands as markers. The solids are three things (`docs/physics.md`): the terrain from `walk.txt` as merged rectangles (`walk.txt` is the ground nobody can stand on, water and cliffs, and holds no objects; its cells that `low.txt` also marks are water an arrow flies over), one rectangle per object from its piece in the kit library (`game/kit/pieces/prop/<zone>_<kind>.json`, `geometry.collision`; an object whose kind has no box there has no solid), and four edge walls outside the picture. A mask taken with `--walk` blocks each object's whole width and must be cut back to terrain by hand. Without `--render`, it rebuilds the base scene from what is already in the folder.
2. Make `<zone>.tscn` by hand (copy `zones/woodland/woodland.tscn`): a `Zone` root, the base instanced as `Base`, a y-sorted `Actors` node for people, signs and camps, `Spawns` markers (one named `start`), and `Doors`. Never edit the base scene; regenerate it.
3. Add the zone to `data/zones.json` and point the neighbours' doors at it.
4. Run `npm run check:godot` and take a 1920 x 1080 screenshot with the recipe above.

**Moving water's budget.** A kit zone's moving water is one strip a stretch of water (`flow.png`, and `flow_<name>.png` for each box in the plan's `water.strips`, each a `Water<Name>` node under `flow_anim.gd`), cropped to what moves in it. Each strip decodes to at most 6 MB of RGBA and a zone's strips to at most 9 MB together (the woodland: about 6.5 MB, `flow.png` 4.5 MB and `flow_rill.png` 2.1 MB, 6.7 MB before the lifts were kept to water; the review of 4 Nov round 3, R3-6: one strip over the rill and the stream was 24 MB). `test_kit.WaterBanks.test_flow_strips_keep_to_the_phone_budget` holds every zone to it.

The woodland's painters (`scripts/art/native/zone.py`, `screen.py`, `water.py`, its plan `art/scenes/woodland.json` and masters in `art/masters/`) came over from `claude-a/woodland-2x` and are now in this repository, so `python3 game/tools/gen_zone.py woodland --render .` redraws it from this checkout (the pictures go to a temporary folder, never `assets/`). From density 3 the kit draws its own way (25 Oct, Matt on the woodland at density 3): crowns and bushes as leaf masses (`foliage.paint_masses`), trunks with bark (`props.trunk4`), water with natural banks and a fall with volume (`water.paint_hd`, `fall_hd`), a footbridge on abutments, the pilot's boulders, ferns, foxgloves and mushrooms at stumps; density 2 is unchanged (`npm run check:kit`). Its walk mask and stands are the 1x zone's own (from that branch's `lib/zone-maps.ts`), edited by hand in `walk.txt` where an object moved (the log and three pines, 25 Oct); do not pass `--walk` again without carrying those edits. Zones from the world canvas (256 px tiles) or from Tiled with YATI will need their own importer writing the same base-scene shape.

## The world editor (27 Oct, first stage)

Kit zones are built from a library of approved pieces rather than painted pictures: `docs/world-editor.md`. `python3 -m scripts.art.kit.build` builds the terrain kit into `kit/terrain/`, and `python3 -m scripts.art.kit.props` builds the pieces into scenes in `kit/props/`. `world/terrain/terrain_ground.gd` draws a zone's `Cells` and `Tiers` layers with `terrain.gdshader`. `tools/kit_zone.gd` turns a JSON plan in `kit/zones/` into a zone scene and back. ## How lanes add a quest

1. Write `data/quests/<id>.json` (copy `woodland_stones.json`): `start.on`, the `steps` with their `on` events and optional `if` and `done_if` conditions, `rewards` in Glint and flags.
2. Give the people in it lines in `data/dialogue/<region>.json`, most specific entry first and an unconditional one last.
3. Place what the events need: an `Interactable` with the speaker id, a `Camp` with the camp id, a door into the zone for `enter:<zone>`.
4. If its places are not built yet, ask for `zone_built:<zone>` in `start.if` (and in the line that offers it), so it cannot half-start.
5. Add a GdUnit test that drives it with `Quests.notify` (see `test/test_quests.gd`), and run `npm run check:godot`: `test/story/test_story_model.gd` then plays it in every order (add it to `PLAYABLE` there once it can be finished in the built zones).
6. Add its steps to a route in `game/tools/routes/` and run `npm run playtest:godot`.
