## Screen handoff

`buildWorldMap({ world, mapSeen, current })` returns detached `nodes`, zone-to-zone `links`, one nullable `suggestion` zone ID and a `visitedSnapshot`. Use `gameStore`/`useGame`'s current `world` and `mapSeen`.

- On the garden/Home screen, pass **`current: 'garden'`**. The saved world spot intentionally remains the resume position when `◀ GARDEN` returns Home; it is not necessarily the active screen.
- In World, pass its live `{ region, x, y }`. Omitting `current` uses the saved spot, falling back to the garden for a first account. Invalid explicit positions produce no current marker/suggestion.
- Capture the result when the map opens. Show its new flags, then call **`markWorldMapSeen(captured.visitedSnapshot)` once per deliberate opening**, not on every render, selector read, frame or walk. The action is idempotent and saves locally. Keep the captured result for that opening if the UI should display what was newly discovered.
- The action never sweeps the latest visited list: a visit made after this snapshot stays new. It cannot acknowledge unknown/unvisited places. No timer, deadline, streak, percentage, daily badge or demand to return is added.

Nodes have stable namespaced IDs (`region:valley`, `zone:town`, `station:valley`), a `kind`, `region`, optional `zone` and `unseen`/`visited`/`here` state. Station nodes also carry their named `stop` ID. Build station markers from that ID, not from region identity: several stops may share a region or zone. Line links carry `fromStop` and `toStop` as well as their zone endpoints. `unseen` means draw an outline, not locked or inaccessible. Zone `col`/`row` come directly from the generated region layout (possibly negative), not old tilted-view or screen coordinates. Labels/art remain Claude's concern.

Region state aggregates its zones; `here` takes precedence. A station is considered discovered when its zone was visited: the current save has no finer station-interaction history. A station is `here` only within the existing `PLACE_RADIUS` of its authored stand, not anywhere in its zone. `isNew` aggregates unacknowledged discoveries and is independent of `here`. The garden is already known. A valid saved position is known even if an old visited list omitted its own zone. A live unsaved location is shown ephemerally; rendering never writes it into saved history.

## Topology, not travel permission

Nodes derive from current generated regions and zones. Edges join zone IDs and distinguish adjacent grid `border`s, inter-region walking `pass`es, existing transport `line`s and the hut `door`. Sunstone Reach is now one `west` region: Gulch–Scorched Pass is an ordinary walking border, and `regionPasses` is empty. Its Gulch and Caldera stops remain separate, joined by the optional mine-cart service. Future authored passes are still supported as distinct walking links, never rail or fast travel. Every zone joins this combined schematic graph, including the Frostline loop and summit spur, the four Tidebloom zones and the hut interior. Current `headland`, `hearthold`, `scorch` and grid positions are preserved.

**A service is not a walking path.** There are now nine named stops in two vehicle networks: seven rail/cart/maglev/elevator/shuttle stops, and the independent `pier–isles` ferry. The combined atlas connects them by the ordinary walking borders between Valley Halt (`halt`) and Driftwood Harbour (`harbour`). `travelRoute('valley', 'isles')` intentionally returns no vehicle route; `travelRoute('pier', 'isles')` returns `['isles']`. Do not join those services with a fictional track, turn a rail into a footpath, treat a whole region as a station, or automatically board on arrival. Walking to the pier and deliberately choosing its existing ferry remain separate actions; no new journey state, auto-transfer, fare or reward is introduced.

For Claude's renderer, `kind: 'station'` means a named transport point, **including ferry terminals**, not necessarily a train station. Choose the service treatment from the stop IDs and current `travelVehicle`, not the generic node kind. The ferry's zone endpoints are `harbour → landing`; the stops are `pier → isles`. Home reaches the atlas through its door, never a fabricated station. These are schematic connections, not proof that painted rails, a pier or a bridge meets its physical endpoint.

The suggestion uses breadth-first schematic hops and stable authored order, ignoring seen badges. It disappears when all known places are visited or the explicit current location is invalid. It does **not** start trips, grant fast travel, alter existing level gates, certify walk-grid reachability or promise the shortest physical walk. The existing walk grids, travel routes and eligibility checks remain authoritative; C23 checks terrain/seam quality. Do not use atlas edges or `unseen` as navigation permission.

## Declared openings

A `border` requires both adjacent tiles and an explicit positive `zonePorts` span. Keys are canonical west|east or north|south, independently of generated tile order. A null, missing, empty or reversed span produces no walking edge: in particular `hollow|woodland` stays closed. The current schematic has 27 open walking borders across 28 declared seams; all 30 zones remain connected through those borders, the real transport services and the hut door. These declarations are topology, not an independent proof of terrain passability. Claude's generator lint and stitched-grid tests remain authoritative; C27's physical route circuits are a separate task.

Every declared seam has an atlas membership check; temporary closed/empty/reversed/missing-port fixtures prove that no walking edge is fabricated and an already-captured map remains detached. The existing seam test's unsafe key assertion is replaced by a key predicate, retaining every port/walk assertion without editing Claude's runtime or generated exports.

## Additive save safety

`mapSeen` is an optional string list in the existing v1 save, required with an empty default in runtime state. The storage key/version stay unchanged. An old missing/malformed list defaults to that account's already known zones, avoiding a migration backlog. An explicitly empty list stays empty. Valid string IDs are deduplicated; unknown future IDs survive storage but are ignored by today's atlas. No balance, player, ownership, collection, companion, history or world-coordinate reset is performed. Existing unknown JSON fields still round-trip through the save codec.

Seen IDs resolve through the authoritative `restoreWorld` visited-zone migration, using a valid current-layout garden anchor and retaining an ID unchanged when it is unknown to that migration. There is no second alias table and no edit to Claude A's `lib/world-save.ts`. Legacy `castle` acknowledgements become `headland`, never `hearthold`, with duplicates removed and unknown future seen IDs retained. Acknowledging an older captured opening also uses that migration so it cannot reintroduce the retired ID. Saved positions use the existing layout migration; explicit live positions and the already-restored saved point are stamped with current `LAYOUT_VERSION` before validation. They must not be interpreted as legacy coordinates a second time. No new migration history or changed world coordinates are introduced.

Named-stop tests include the actual two Sunstone stops, plus two stops sharing one zone with distinct proximity and service identities. Layout-1 Caldera and layout-2 valley positions restored by current production code retain the right atlas marker. All current-zone fixtures explicitly stamp today's layout rather than accidentally masquerading as historical coordinates. A separate process simulates a next-version migration boundary against the actual builder/restorer: an old saved spot migrates once, live/Home positions stay current, unknown future layouts do not misplace an explicit live marker, and rendering never mutates saved discovery. This boundary fixture does not validate any unimplemented layout history.
